# BLKTable

## What this project is
A custom, in-house web app for BLK that borrows Airtable's *concept* (tables of records, add new tables over time) but is our own site and code — not built inside the Airtable product. Each table has two faces: a public shareable form link anyone can submit through (no login), and a private login-gated dashboard where the team reviews and manages submissions.

- **A record you can add by hand (all tables, 2026-08-13).** Every row in the app used to be born from a public form submit or an import — there was no way to type one in, and the `+` on the grid header adds a *field*, not a row. A blue **＋ New record** now sits in every table's base bar, shown on `can_edit` rather than admin, because adding a row is the same permission as changing an answer already on file. It follows the public form's rules rather than inventing new ones: a question that does not apply carries no answer, an empty answer stores no key at all, and only the questions being asked can be required. Staff-only questions *are* shown, since the person typing is staff. The editor rows are the record panel's own rows, factored into one `edFieldRowHtml()` that both call. The write goes through a SECURITY DEFINER `create_record()` so it can enforce "a table you can edit" — a broad `authenticated` INSERT policy would let any login write into tables they cannot open. **Needs `09-create-record.sql` applied.**
- **One public link per record, not just per table (all tables, 2026-08-13).** A table can declare `config.parent = {table, title, show}` and its form is then served per parent *record* at `/f/?t=<slug>&e=<token>` — the same public page with one extra parameter, one rotatable token per row, and every submission stamped `parent_id`. Anon's view stays narrow: it gets only the fields `show` names, via `get_parent_details()`, never the parent row, and `config_public` carries only the marker `{"scoped": true}`. A scoped form with no token, or a token from another table's record, is "not found" rather than a form that fails on submit. A parent record's panel carries its link, QR, copy and regenerate, for managers only. Built for Events (one signup form, one link per event) and wanted by the Operate tasks per branch. **Needs `10-parent-scoped-form-links.sql` applied** — though the page works either side of it, on purpose.

- **A form that fills up, with backup places behind the real ones (all tables, 2026-08-13).** A child table declares `config.capacity = {slots, backup, open, full}` and the *numbers* live on the parent record, so every event sets its own; `open`/`full` are stage keys from the parent's own `config.stages`, so nothing in the engine is events-specific. The parent row is locked `FOR UPDATE` while the count is read and the row inserted, because a count read outside a lock is a count that *was* true — two people on the last place cannot both take it, and the flip to *filled* happens inside the same lock. `submit_public_form` returns jsonb now so the confirmation says "you have a place" or "you are on the backup list". An **empty capacity number means no limit**, so declaring capacity changes nothing for records carrying no number. Also carries the gate that a link accepts signups only while the parent's status is `open`. **Needs `11-capacity-and-backup.sql` applied.**

- **A question that takes a video, not only a photo (all tables + future ones, 2026-08-13).** A new `media` field type sits beside `photo` and accepts `image/*,video/*`. The existing `photo` type is untouched, so all 226 tables behave exactly as before; this is an addition, not a change. Built for Operate's task checklists, which have **59 "Media" questions** across the 33 tasks, and it also gives the **238 imported applications whose upload was a video** somewhere to be shown — those files have been in R2 since the migration with nothing able to point at them, because a photo field only ever points at something a browser can render.
  - **The type is derived from the key, because nothing else knows.** A stored answer is a bare R2 object key (`<uuid>_<original filename>`) with no MIME type beside it and nowhere to put one without changing the shape of every answer in the app. So image-vs-video is decided from the extension, which survives sanitising. A key with **no** recognisable extension reads as an image — which is what every row written before this existed is.
  - **What a browser will play is narrower than what people upload.** `.mp4/.mov/.webm` play; `.avi/.mkv/.wmv` are still stored and still downloadable, but are offered as a link rather than handed to a player that would show a black rectangle and no explanation.
  - **A video has no thumbnail**, because the hourly sweeper builds them from images. Anywhere a thumbnail would go — card cover, grid cell — it shows a play mark instead. Painting one would have produced an empty grey box that reads as a card that failed to load. Poster frames need ffmpeg on the server and are separate work.
  - **Two ceilings, and they are said before the upload, not after:** 10 MB for a photo, 50 MB for a media question, because a phone photo is 2–4 MB and ten seconds of 1080p is 20–30 MB. Refusing an 80 MB video after it has crawled up shop wifi is the failure this is designed around.
  - **The `r2` edge function is deployed and video upload is live (2026-08-13).** It previously rejected any non-image and capped at 12 MB. Now `video/*` is accepted with its own ceiling (`R2_MAX_VIDEO_MB`, default 50), images keep theirs at 12, and `/health` reports both so the running version can be identified without uploading anything. **Verified against the live function rather than assumed:** a photo still uploads (what all 226 forms use), a non-image/non-video is still refused, a 45 MB video uploads in ~11s without the container restarting, a 60 MB video is refused at 50 and a 13 MB *image* at 12 — so the cap is per kind, not one number. Test objects were deleted from the bucket afterwards.
  - **The deployed function was ahead of our copy of it, and that nearly cost the audit fix.** The 2026-08-12 audit added the staff-profile check to `isStaff()` on the server and it was never brought back into the private repo, so deploying our file would have silently reverted it. The media change was rebased onto the *deployed* source instead, and the repo copy now matches the container byte for byte. **A file edited straight on the server is a file that will be overwritten by the next deploy** — worth remembering for `admin-users`, which has the same shape.
  - **Where an upload is shown, now that there are two panels.** The record panel has a read-only form and an editable one, and only the read-only one listed uploads as a labelled gallery — the editable one (what an admin, editor or manager sees) showed a single image as a header instead. Since a video is never that header, a video was invisible to exactly the people who review them. **Both panels now render the gallery**, the editable one skipping the still image already shown as its header so it is not repeated. Photos: header + gallery. Videos: a play tile that opens full-size in the lightbox with controls.

- **A status that is worked out, not pressed (2026-08-13).** `config.capacity.window = {date, start, end}` names the parent's own questions, and the phase is derived every time it is read: *Done* once the end time passes, *Running* between start and end, *Filled* when every place is gone, *Open* otherwise. Nothing stores it and nothing schedules it — which matters because `pg_cron` is still not installed, and a computed value cannot go stale if a job stops. Signups close when the event **starts**. Absent the window, the previous stored-status behaviour applies untouched, which is what all 226 other tables have. The rule exists twice (JS + `event_time_phase()` in SQL) for the same reason `condMet` does; they were compared case by case and differ only on unparseable input, where the server errs open and the dashboard shows nothing.

## Decisions made
- **Own code, not Airtable:** user explicitly rejected building inside Airtable; we only mimic the idea.
- **Empty Airtable tables are not recreated (2026-08-10).** 52 of the 290 tables hold zero records — mostly the Iraq bases and unused `Table 2`s. Asked and answered: leave them. Migration means data, not empty shells; anything genuinely needed can be built in the table builder in a minute.
- **Everything from the final sweep lands archived, and what becomes visible is a human call.** A generated table appearing beside the live hiring table is how the data gets confused; archiving first and promoting deliberately is the safe order.
- **Stack:** GitHub Pages (static) + Supabase, same as the Qahwa site. No framework, no build step — keep it simple.
