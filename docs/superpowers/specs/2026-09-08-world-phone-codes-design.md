# Every country's dial code on the phone question, pre-filled from the device and searchable

Date: 2026-09-08
Status: design, approved in conversation, not yet implemented

## The problem

The `phone` field type offers four countries. `COUNTRIES` in `f/index.html` holds Jordan,
Lebanon, Syria and Iraq, hardcoded, and the picker always opens on Jordan because the last
line of the branch is `apply(0)`. There is no detection of any kind, and no way to search a
list of four because a list of four does not need one.

Three things follow from that, and all three are already happening.

**Foreign numbers arrive anyway and are filed under the wrong flag.** Of 44,631 stored phone
answers, roughly 600 carry a dial code the picker cannot represent: +972 (113), +970 (59),
+971 (40), +966 (30), +974, +201, +965, +905, +973, +49, +44, +250 and more. The picker gave
those people a Jordanian flag and a box, so they typed their country code into the local
number and the answer reads as a Jordanian number with too many digits.

**The record editor corrupts them on save.** In `index.html`, `parsePhone` matches a stored
value against `COUNTRIES_ED` and falls back to `{ idx: 0, local: v }` when nothing matches.
So a record holding `+971501234567` opens showing a Jordanian flag beside `971501234567`,
and saving writes `+962971501234567`. The 33,795 legacy answers stored as a local `0…`
number are rewritten the same way. This is the same shape as the data loss the date box had
before PR #122: the panel looks right, and the save is what destroys the value.

**Two lists of four already drifted once.** `COUNTRIES` in `f/index.html` and `COUNTRIES_ED`
in `index.html` are the same data written twice, and commit `6cc5a29` ("a second var
COUNTRIES broke every phone question on the public forms") is what happens when a third copy
appears.

The country question, meanwhile, is pre-filled from the device timezone and has been since
PR #146. The phone question, sitting directly beneath it on Customer Complaints and Contact
Us, is not.

## What we are building

Every phone question, on all 47 of them across 43 tables, offers all 245 dial codes. The
country is pre-filled from the device's timezone and stays changeable, and the list is
searchable rather than scrollable. Validation becomes per country rather than one generic
rule: each country's own valid lengths and its own number pattern.

No database migration, no new RPC argument, no change to the `countries` table.

## Part A: the data

Two tables, generated by one committed script, inlined into both pages.

`tools/gen-phone-data.js` reads three pinned sources and writes the shared block:

| Source | Pinned version | What it gives |
|---|---|---|
| `libphonenumber-js` `metadata.min.json` | 1.11.17 | dial code, valid lengths, national number pattern |
| `libphonenumber-js` `examples.mobile.json` | 1.11.17 | one real example number per country |
| `countries-and-timezones` | 3.6.0 | zone to country, primary country per zone |

**Table 1, the dial rows.** `PHONE_ROWS`, 245 countries, each one
`iso2~dial~lengths~example~pattern~name` (format settled below). Every country in the
metadata has both a length set and an example number, so there are no gaps to paper over. The
example number becomes the local box's placeholder, so a German picker stops showing a
Jordanian shape.

**Table 2, the zone map.** `TZ_ISO`, 541 `zone~iso2` pairs.

Two facts about that map that decide whether it is right or quietly wrong:

* **109 IANA zones are claimed by more than one country**, because tzdata gives one canonical
  zone to every country sharing its rules. `Africa/Abidjan` covers twelve, Iceland among
  them. Reading a zone to country map naively out of tzdata metadata produces `Asia/Dubai` to
  French Southern Territories, `Asia/Riyadh` to Yemen and `Europe/Berlin` to Svalbard. The
  generator therefore takes the primary country per zone (`getCountryForTimezone`), which is
  the first country on the zone's `zone1970.tab` line, and the one the zone is named for.
* **Deprecated zone names must be in the map.** Browsers still report `Asia/Calcutta`,
  `Europe/Kiev`, `Asia/Rangoon` and `America/Buenos_Aires`; ICU treats several of those as
  canonical. The canonical list alone is 311 pairs, and India, Ukraine, Myanmar and Argentina
  are absent from it. Including deprecated names takes it to 541. Verified, not assumed.

Five countries in the zone map have no dial code in libphonenumber (AQ, GS, TF, UM, PN, all
uninhabited or research stations). They fall back like an unknown zone.

**Country names come from the page, not from the packages.** `COUNTRY_NAMES_ALL` already
holds the 197 names the country question stores, and the packages disagree with seven of
them. Measured, so the override map is known rather than discovered later:

| ISO2 | package says | we store |
|---|---|---|
| CG | Republic of the Congo | Congo (Brazzaville) |
| CD | Democratic Republic of the Congo | Congo (Kinshasa) |
| CI | Ivory Coast | Cote d'Ivoire |
| TR | Türkiye | Turkey |
| US | United States of America | United States |
| VA | Holy See | Vatican City |
| XK | (absent from the zone package) | Kosovo |

Those seven are the whole override map. The generator applies them, then asserts that each of
the 197 page names appears exactly once among the emitted names; verified as 0 missing. If
that assertion ever fails the generator refuses to write, because a changed name string is a
country question whose stored answers stop resolving. The 52 dial-code territories with no
name in our list (Aruba, Anguilla, Guernsey and friends) take the package's name.

Kosovo is worth its own line: libphonenumber knows it as XK on +383, and
`countries-and-timezones` does not carry it at all. So Kosovo has a dial code and a name but
no zone, meaning it can be chosen and never guessed.

**Inlined, not fetched.** Both tables go into `index.html` and `f/index.html` as a shared
block, byte identical, pinned by a parity test the way the date and time block is. An
`assets/` file would be one network request the public form cannot submit without, and the
form's whole job is to submit from a shop on bad wifi. The cost is 26.5 KB of dense text on
each page, measured on the real packed output (16,274 bytes of dial rows and 10,228 of zone
pairs, as they land in the page). The public form is 171 KB today, and Fastly serves it
gzipped.

**The packed format, settled by measurement.** Fields separated by `~` and rows by `;`,
because the patterns themselves contain `|`, `,` and `:` and would corrupt one country
silently. Neither `~` nor `;` occurs in any pattern, name or example number. Lengths are
base36 digits, one character each, since the largest possible length is 17. No pattern
contains a double quote, and the 779 backslashes are escaped by emitting the table through
`JSON.stringify`, so `\d` survives as `\d` rather than becoming `d`. A row reads:

```
JO~962~89~790123456~(?:(?:[2689]|7\d)\d|32|53)\d{6}~Jordan
```

Each table is emitted as a **single-line** `var` declaration, because `grabVar` in the test
harness matches `var NAME = [^\n]*;` and a multi-line declaration reads as missing.

Proven before this was written: all 245 example numbers validate against their own row's
lengths and pattern, and all 197 page names resolve to a dial row.

## Part B: the picker

The phone row keeps its shape: flag and dial button, then the local number input. What
changes is what opens when the button is pressed.

`.cc-menu` becomes a searchable panel: a search input at the top, a height-capped scrolling
list under it, flipped above the button when there is no room below. The filter matches
country name, dial code with or without a `+`, and ISO2 code, so "ger", "49", "+49" and "DE"
all find Germany.

The interaction rules are the ones `buildCombo` already establishes in `f/index.html`: type
to filter, ArrowUp and ArrowDown to move, Enter to pick the highlighted row, Escape to close,
and a "No matches" line when nothing matches. Same idiom, in the `cc-menu` shape rather than
replacing the phone row with a combo, because the row's compact flag button is what makes it
read as a phone field and not a second dropdown.

**Jordan, Lebanon, Iraq and Syria stay pinned at the top** of the unfiltered list, above a
divider, with the remaining 241 alphabetically after them. Filtering searches all 245. The
pinned four are also the escape hatch for a wrong guess: one tap back to where nearly all
the traffic is.

## Part C: the pre-fill

`phoneCountryFor(zone)` resolves the device zone through the zone map to an ISO2, then to a
dial row. It falls back to **Jordan, exactly as today** when the zone is unknown to the map,
when the zone has no country (`Etc/UTC`, Antarctica, and a hardened browser reporting `UTC`),
or when the country has no dial code.

It runs per phone control, after `restoreAnswers`, and **never over an answer that already
exists**. A restored draft holding `+96179…` sets both halves through `splitPhone` and the
guess does not touch it. `current` wins, the same rule `prefillCountryName` states for the
country question.

`options.prefill: false` on the phone question opts it out, matching the convention migration
67 established for country questions. Note this reads the flag on the phone field itself:
Franchise's country question carries `prefill: false` because "which country are you
interested in Franchising in?" is intent rather than location, but its phone question is
genuinely asking where the person is, so Franchise phone numbers do pre-fill.

**The hazard, stated so it is not discovered later.** A Jordanian in Germany gets `+49`,
types `0791234567`, and it passes: 9 digits is inside Germany's length set and the digits
match Germany's pattern. The result is an unreachable number stored more confidently than a
Jordanian number in an empty box would have been. This is the same trap the country
pre-fill introduced, moved onto the field that WhatsApp actually dials.

Two mitigations, both cheap. The pinned four keep the correction one tap away. And the row
carries a hint whenever the code was guessed:

> Country code set from your location, change it if your number is from somewhere else.
> تم تحديد رمز الدولة من موقعك، عدّله إذا كان رقمك من مكان آخر.

It is removed the moment the code is changed, driven the way `syncPrefillNote` is: from the
code that settles the choice, not from a DOM listener, because the picker settles a choice in
code and fires no event a listener would see.

## Part D: validation

A number is valid when `digits.length` is in the country's length set **and** the digits match
the country's national number pattern. Length alone is not a rule for 29 countries whose sets
span six or more values (the UAE accepts 5 to 12 digits, Germany 4 to 15), and for our own
four it would accept `999999999`.

Leading zero stripping stays as it is. It is correct nearly everywhere and it is the fix for
the most common entry mistake here, a Jordanian number typed with its trunk 0. It is wrong for
Italian landlines, which keep the 0. That is a known and accepted inaccuracy, recorded here
rather than solved, because losing the trunk-zero fix would cost far more than Italian
landlines are worth to us.

Required-question behaviour does not change: an empty optional question is still valid, and a
failing required one still blocks submitting.

**What this does to our four.** The per-country rules are looser than the hand-written ones,
because they include landlines:

| | today | after |
|---|---|---|
| Jordan | exactly 9 | 8 or 9, matching the Jordanian pattern |
| Lebanon | 7 or 8 | 7 or 8, unchanged |
| Syria | exactly 9 | 8 or 9 |
| Iraq | exactly 10 | 8, 9 or 10 |

So an Amman landline is newly accepted, and `999999999` is newly refused. Accepted
deliberately: a landline cannot receive the WhatsApp message this field feeds, but refusing a
real number on a required question loses the whole submission, which is worse. The hint under
the field already says "We may contact you on WhatsApp."

For the 12 shared dial codes (+1 across 25 countries, +44 across 4, +7, +39, +47, +61, +212,
+262, +290, +358, +590, +599) a typed number is accepted when it matches **any** country
sharing that code. Parsing a stored number back to a country is ambiguous by nature for
those: the flag shown is the first country on the code, the number itself round-trips exactly.
The flag is a guess, the digits are not.

## Part E: the record editor, and the corruption fix

`COUNTRIES_ED` is deleted. `index.html` reads the same generated table as the public form, so
there is one list rather than three, which is the condition that produced `6cc5a29`.
`phoneCountry` (the flag beside a job applicant) and `countryFlag` (which derives a flag from
`countries.dial`) fold onto the same table.

`parsePhone` gets longest-dial-first matching, as `splitPhone` already has, and stops
guessing:

| stored value | picker | local box | what save writes |
|---|---|---|---|
| `+962791234567` | Jordan | `791234567` | recomposed, as today |
| `+971501234567` | UAE | `501234567` | recomposed, correctly |
| `+170123` (junk, and ~100 rows of it exist) | unknown code | raw value | **the original string** |
| `0791234567` (33,795 legacy rows) | unknown code | raw value | **the original string** |

The last two are the fix. An untouched value is returned unchanged, using the `data-touched`
flag the date and datetime boxes already use for exactly this reason: an empty or unparsed box
is otherwise indistinguishable from a cleared one. Once somebody edits the number, normal
composition resumes and the value is theirs.

The editor does not validate, today or after this change. Nothing about a stored number can
block a save.

## Part F: the country question, worldwide

Adjacent to the request rather than part of it, and separable: strike this part and everything
else still stands.

`zoneCountryName` reads `countries.timezones`, which holds four zones. So a Berlin visitor
gets `+49` on the phone question and nothing on Country, even on a form that offers all 197
names. Adding the embedded zone map as a fallback **after** `countries.timezones` makes the
country pre-fill work worldwide for about five lines.

Order matters: the database stays authoritative, so an admin can still correct or add a zone
without a deploy, and the embedded map only answers what the four rows do not.
`countryChoiceNames` still filters the result, so a form scoped to ["jo", "lebanon"] fills
in nothing for a German visitor rather than offering Germany.

## Testing

Unit tests, `docs/tests/phone-world.test.js`:

* every one of the 245 dial codes round-trips through `splitPhone`
* each country's own example number validates against its own row, 245 assertions the
  generator provides for free
* numbers valid for our four today are still valid; one digit short fails; `999999999` fails
  for Jordan
* zone map: `Asia/Amman` to JO, `Asia/Dubai` to AE, `Africa/Abidjan` to CI, `Asia/Calcutta`
  to IN, `Etc/UTC` to the Jordan fallback
* `parsePhone` returns the original string for an unparsed value and for a legacy `0…` number

Falsification, because a green first run proves nothing here (see the concurrency and
double-tap tests that passed while testing nothing): break the pattern check and confirm the
"one digit short" case fails; **stub `window.Intl` to report `Europe/Berlin`** and assert the
picker lands on +49. On a machine in Amman, hardcoding `Asia/Amman` passes every value
comparison in the suite, so the only proof the zone is read is swapping it out from under the
page.

Chrome tests, `docs/tests/phone-picker.chrome.js`:

* open the picker on a real public form, type "ger", press Enter, assert the dial reads +49
  and the placeholder is a German example
* type a number, submit, assert the stored value
* the regression: open a record holding `+971501234567` in the editor, save without touching
  the phone row, assert the value is unchanged

Parity: the shared block is byte identical in both pages, and `COUNTRIES_ED` no longer
appears anywhere.

## Deployment and rollback

Page only, so there is no migration-before-page hazard and no ordering to get right. Merging
the PR deploys it to GitHub Pages. Rollback is reverting the PR.

Verification is on the deployed page rather than in the suite: open `franchise-apply` and
`customer-complaints` live, confirm the pre-filled flag, search for a country, and submit one
test answer through an alert-free form (`notify_on_submission` returns early unless
`config->'alerts'` is an array), then delete the row.

## What is deliberately not here

* **No rewriting of existing answers.** The ~600 foreign-code answers and the 33,795 legacy
  local numbers stay exactly as they are. This change stops the editor corrupting them; it
  does not touch them. A read-only audit of numbers whose stored code matches no real country
  (the +170, +181, +146 junk) is a separate piece of work.
* **No mobile-only validation.** The general pattern accepts landlines, per Part D.
* **No runtime libphonenumber-js.** A 150 KB CDN script the public form's required question
  depends on is an outage waiting for bad wifi. The metadata is embedded instead, and
  refreshing it in a year is running the generator and committing the diff.
* **No `submit_public_form` argument, and no `countries` rows.** Adding an argument to that
  RPC breaks all 226 forms, and adding roughly 200 rows to `countries` would reach the country rail,
  `table_access` country scopes and branch grouping. Neither is needed: the picker is page
  data and the answer stores itself as the string it always was.
