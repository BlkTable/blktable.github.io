# Tests

There is no build step and Node is not installed standalone on the dev machine,
so the tests are plain scripts run with the Node that ships inside VS Code:

```bash
cd C:/Users/ASUS/blktable
ELECTRON_RUN_AS_NODE=1 "C:/Users/ASUS/AppData/Local/Programs/Microsoft VS Code/Code.exe" \
  docs/tests/shell-helpers.test.js
```

The one exception is `card-panel.chrome.js`, which drives the panel in headless Chrome;
it finds Chrome or Edge itself, and skips instead of failing when neither is installed.

Run them from the repo root — each one reads `index.html` and pulls the functions
it tests out of the page by name, so there is nothing to keep in sync by hand and
a renamed function fails loudly instead of silently going untested.

| `card-customise.test.js` | "Customize cards" — which file question is a card's cover, whether it is cropped or fitted, which fields the card carries and in what order, and whether their names show (`cardPrefs`, `summaryFields`, `cardChoosable`, `cardSave`, `coverHtml`). | `card-panel.chrome.js` | the same panel, **clicked**: the arrows, the tick boxes, Crop/Fit, the cover radios and Reset, driven in order with the answer read back out of storage. The only file here that needs more than node — headless Chrome, found automatically or named with `CHROME=<path>`, and **skipped rather than failed** when there is none — because reorder and "the last field cannot be unticked" are DOM and events, and a panel whose arrows quietly stopped working would pass every other test in this folder. | `sidebar-groups.test.js` | the sidebar's left edge (`groupByCategory`, plus the two fold headings read out of `index.html` as source). The tests that matter are the ones about *not* losing anything: a flattened table keeps its place in the list rather than being appended after everything else, the category is still on the row so it groups again by itself the moment a second table joins it, and the width of `.side-fold` is compared against `.tmark` in the stylesheet so the two cannot drift |
| `duplicate-table.test.js` | duplicating a table (`duplicate_table` is a database function that verifies itself when applied — see `workspaces/19-duplicate-table.sql`; these test the page). Every test is a way the feature could ship looking finished and not be: the item missing from one of the two ⋯ menus, which are separate code built two separate ways; a non-admin being offered it; the copy being made but never opened, so it is lost in a sidebar of 272 entries; "copy the records too" defaulting to on, which for the biggest table copies 28,000 rows because somebody clicked through a dialog; and a missing migration reading as a permissions problem, which is exactly what `record_share_token` did for a week |

The tests are the two halves of that: the metadata survives a round trip through the editor and goes back untouched, and it is never mistaken for a URL button — including a half-written one that has lost its name, which must still count as a linked record rather than falling through to the URL rule. Three assertions read the save as source, because the order matters: the linked-record check has to run *before* the URL rule or it still rejects the save first |
| `builtin-public-title.test.js` | the heading `/apply` and `/cast` print, which is **not** the table's name (`builtinPublicTitle`, `serializePublicTitle`, `setPublicTitleInputs`, plus `applyHeading` read out of both public pages). The table is called "Job Applications"; the page says "Job Application · طلب توظيف" — so renaming the table could never reach the page, and pretending it did would have shown applicants a heading they never see. The heading is its own setting (`config.title`), carried by `get_form_config`, which returns the built-in table's config as it is. Most of the tests are about **not** breaking the pages that have no title set — which is all of today's traffic: no title, a `null` title (what two empty boxes actually store) and a whitespace-only title must all leave the served heading exactly as it was. The rest are the ways a bilingual heading goes wrong: each half falls back on its own so setting only the English cannot blank the Arabic, two empty boxes store `null` rather than an empty object that reads as "set", the markup keeps its own heading so the page reads correctly before the request completes and if it fails, and the text is set with `textContent` and never `innerHTML` — it comes from the database and is typed by a person. The rule exists three times (the dashboard preview and both pages) the way `condMet` does, and the tests load all three so they cannot disagree about what the applicant is looking at |
| `form-live.test.js` | whether a public form's link is live — `app_tables.is_active` (`linkLive` from `index.html`, plus `setFormLive` and the `f/index.html` lookup read as source). **Recovered from `design/airtable-form-parity`, where it was written and never merged**, while the feature it covers has been live since #37 — which shipped with no tests. This is the flag behind the worst bug the project has had: nothing in the app ever wrote it, so on 2026-08-17 the Contact Us link answered "Form not found" on launch day along with **176 other form tables**, while the Form tab drew a link and a QR code for every one of them. The tests cover the deliberate asymmetry in `linkLive` — a **missing** flag counts as LIVE, because a row loaded before the column was selected must not be reported as a dead link — that the Postgres text `'f'` reads as live (a guard on the shape of the data, since `'f'` is truthy in JS), that the flag is read in one place rather than hand-copied, that the write is scoped to one table id (a bare update would publish or unpublish every form at once), that switching a form **off** is confirmed while switching it on is not (off is the direction where a printed QR code silently stops working), and that the public page still filters on the same flag — if it stops, the switch in the app becomes decoration. Two assertions were rewritten on recovery because they pinned spellings main has since improved on: the write gate widened from `isAdmin` to `mayModifyTable` (admin **or** the table's creator), and the not-found guard now routes through `resolveAliasOrNotFound` so a retired slug forwards instead of dying; both now assert the rule and were re-proved to catch an ungated switch and an unfiltered lookup |
| `form-country.test.js` | which country a form is for, and the franchise family (`builderConfig`, `fieldRowsFor`, `tableCountry`, `isFranchiseParent`, `branchListMismatch`, plus the create path, `writePendingConds`, `setBuilderChrome` and the Countries manager read out of `index.html` as source). The thing being undone here is worth stating: a `Country` question was appended to every new table and back-filled onto all 260, so **260 forms asked the public which country they were in and 4 records ever answered** — 10 of the 14 answers say "Jordan". The country is a property of the form, so the first test is that nothing appends one any more and that exactly **one** place in the page still writes a country field: the parent of a franchise family, where asking is the point. The rest are the ways the family could go wrong quietly — the parent's country question not first or not required, the designed questions not shifted down to leave room for it (and `writePendingConds` not shifted with them, which is a conditional question gated on the answer to a *different* question, invisible because both pages would agree and both be wrong), a sub-form that does not record its own country or point back at its parent, five inserts fired at once against one slug prefix, and a half-created family reporting "could not create" while three real forms with real links already exist. The Countries manager's tests are all "a shop is never deleted": its name is the answer on every record ever filed against it, so closing it is a flag, a rename to nothing is refused, a move between countries is confirmed, and a duplicate name says whether the namesake is merely switched off |
| `no-application-history.test.js` | that the second Job Applications sidebar entry is **gone** and cannot come back (`jaScoped`, `loadFacets`, `openJa`, `paintBuiltinNames`, plus the markup and the sidebar handler read as source). `origin` split one table into two entries and the imported side was where **33,789 real applicants sat unread**; `workspaces/31` moved all of them onto the board, so the entry listed nothing. Every test is source-read on purpose, because what was removed is *reveal* code — a sidebar row, a scope default, a name suffix — and this project has shipped three features that were live and unreachable precisely because nothing tested the reveal. | `ballot-field.test.js` | the ballot — a `record_multi` question whose choices are another table's live rows (`ballotLabel`, `ballotOptions` from `f/index.html`, `ballotNames` from `index.html`). The test that matters is about the stored **value**: it is the record id and never the printed name, so renaming an event cannot orphan a vote — the same rule that stops every other config in this app matching questions by label. The rest are the ways an empty ballot reads: no events, a failed RPC, and a database that does not have `ballot_options` yet must all render the form with a "nothing open" line rather than a blank box or a dead page, because the page and the migration have to be deployable in either order (the `p_token` lesson). A dateless event sorts last rather than heading the list, matching what `ballot_options` already does in SQL. On the display side, ids are exact storage and useless to read: `ballotNames` resolves them, and an id whose event was deleted is **named** as deleted rather than dropped, since a vote for a deleted event must not look like a vote nobody cast. Two assertions compare a label against the same event without a rate rather than grepping for digits — `2026-09-10` contains both a 20 and a 10, so a digit search would have tested nothing |
| `poll-links.test.js` | one link per poll, and the picker that fills it (`recordOptsLabel`, `edChecksKeyed`, `linkLive` from `index.html`, plus the three link gates and the ballot payload read as source). A poll is a record, so the link machinery is Standard 1's and the only new UI is a question type: `record_multi`, whose checkbox **value is a record id** and whose text is a label built from the source table's own `card_fields` — the first of which is already that record's title everywhere else, so this cannot drift from what the cards show and nothing looks a question up by its label. The rest are the ways this ships looking finished and is not: `edValues` must route `record_multi` through `edChecksValue` or the picker renders, ticks, and saves nothing; the source records must load before an editor is drawn or the picker is empty; and the three per-record link sites must all gate on `linkLive(child)` — without it every event offered a link and a QR code for the **roster** form, which is switched off and which nobody fills in over the web. | `assign.test.js` | the roster panel's reading half (`assignConfig`, `assignPersonKey`, `assignCandidates`, `assignMonthCount`, `eventsOverlap`, `assignClashes`). The rule Zamel asked for is one test: somebody who voted for A and B is **not** offered for C. Around it are the ways that goes quietly wrong — `e-1` matching `e-12` by substring, and a barista who votes again being listed twice instead of replacing their earlier answer (**the latest vote decides**, so withdrawing a tick actually withdraws it, and array order never decides — `created_at` does). Identity is `trim().toLowerCase()`, the same rule `payrollRows` uses: if the two ever disagree, the roster and the money disagree about who somebody is. Votes cast under different poll links both count, because the tick names the event, not the poll. The clash tests pin the half-open reading of a shift: 10–16 and 16–20 are two shifts one person can work, a missing end time is the end of the day, and an end before its own start is too — which is what `eventPhase` already does, and two rules about one pair of times that disagree is how an event reads as over before it began |
| `assign-submit.test.js` | the **caller** that writes a roster (`assignDiff`, `submitAssignments`), database stubbed, assertions about the calls made and their order. `payroll.test.js` passing 16/16 while the export was broken is why this file exists. The one test the feature lives on: **a re-submitted roster with no change must not touch the database at all** — every write is a queued message, so a careless save re-messages the whole team and the feature is switched off in week one. Beside it: a slot change is an `update` and never a delete-plus-insert (which would re-fire the INSERT-only trigger and tell somebody twice), a missing slot counts as confirmed on both sides so old rows do not all look changed, a duplicate row for one person is trimmed to one rather than re-added, inserts go **last** so nothing is messaged before the removals land, and a failed delete stops before anything is inserted. Two assertions are about where slot lives: it is written as the **native `app_submissions.slot` column**, because `payrollRows` filters `s.slot` — a slot inside `data` leaves that column null, drops every row from `only_slot:'confirmed'`, and makes every export read "nothing in that range", which is how the export broke on 2026-08-17. The rest read the page as source: the button follows `can_manage` like Payroll, `openAssign` re-checks it so the gate does not live only in the markup, submitting never touches the event's status, and the write never enforces capacity |
| *(multi-day, folded into the three files above)* | an event can span days (`eventDays`, `ballotKey`, `assignRowKey`, plus the day arm of `assignCandidates`, `assignDiff`, `assignMonthCount`, `assignClashes` and `ballotNames`). A vote names one **day** of an event, stored as `<id>#<date>`, so a barista can take the Friday of a three-day fair and not the Saturday — and the tests that matter are the ones where days must not bleed: `e-9#Friday` is not matched by a Saturday query, a day-bearing vote is not matched by a dayless one, and a person who ticked Friday and Sunday is offered on neither Saturday. On the roster the identity is **person + day**, not person: keyed on the person alone, Day 2's row reads as a duplicate of Day 1's and saving Day 2 deletes Day 1. One row per person per day is also what makes the money right with no payroll change — `payrollRows` adds the event's rate once per row, so two days of a 15 JD event pays 30. `eventDays` is pinned on the ways a range goes wrong: inclusive at both ends, across a month, across a year, across a leap day, an end **before** its start reading as one day rather than zero, no date at all reading as one unnamed day so a dateless event stays tickable, and a mistyped year capped at 60 rather than drawing hundreds of boxes. `ballotNames` splits the day back off, because looking the whole key up as an id would print "(deleted event)" against every good vote |
