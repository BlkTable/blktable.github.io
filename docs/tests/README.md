# Tests

There is no build step and Node is not installed standalone on the dev machine,
so the tests are plain scripts run with the Node that ships inside VS Code:

```bash
cd C:/Users/ASUS/blktable
ELECTRON_RUN_AS_NODE=1 "C:/Users/ASUS/AppData/Local/Programs/Microsoft VS Code/Code.exe" \
  docs/tests/shell-helpers.test.js
```

The one exception is `card-panel.chrome.js`, which drives the panel in headless Chrome;
it finds Chrome or Edge itself, and skips instead of failing when neither is installed.

Run them from the repo root — each one reads `index.html` and pulls the functions
it tests out of the page by name, so there is nothing to keep in sync by hand and
a renamed function fails loudly instead of silently going untested.

| file | covers |
| --- | --- |
| `shell-helpers.test.js` | Home's recently-opened grouping (`periodOf`, `groupByPeriod`, `agoText`), per-table colour and glyph (`tableTint`, `tableGlyph`), and the filter engine's condition groups (`passesList`, `filterCount`, `pruneConds`, `condSlot`) |
| `conditional-questions.test.js` | "ask this only if" (`condMet`, `condLabel`) — and it loads `condMet` from **both** `index.html` and `f/index.html`, asserting the same answer from each, because the public form and the review panel each carry a copy of the rule |
| `flag-tag.test.js` | the red "needs noticing" mark (`flagTagHtml`) — which answers trip it, that a blank answer never does, that matching ignores case, and that the admin-typed label is escaped |
| `payroll.test.js` | the date-range export (`payrollRows`, `payrollConfig`, `inDateRange`, `payrollNumber`) — the output is money somebody is paid, so every test is either "a row was quietly dropped" or "money went out twice": both ends of the range inclusive, an event with no date never in range, a rate that is not a number reading as 0 rather than NaN, a backup who never worked not paid, a signup whose event was deleted earning nothing, `Ahmad`/` ahmad ` counted as one person while genuinely different spellings stay separate (as decided), and a nameless signup kept as `(no name)` rather than dropped |
| `swap.test.js` | moving somebody between confirmed and backup (`slotPillHtml`, `slotActions`, `slotCountText`) — that a table where nothing holds a place is untouched, that confirmed and backup differ by colour and not only wording, that the pill's classes actually exist in the stylesheet, that only the move you are *not* on is offered and only to a manager, and that a place move is intercepted before the WhatsApp/Call/Email dispatcher it borrows its menu from. The two rules that protect the count — the trigger promoting the oldest backup on delete *only*, and a promotion into full places being refused under a lock — are database behaviour and are checked in `13-swap-and-promote.sql` |
| `one-per-browser.test.js` | one submission per browser (`alreadyText`, `deviceKey` from `f/index.html`) — that a backup is never told they have a place, that the key is minted only for a form that opted in, that `p_device` is added to the payload conditionally (a fourth key against a three-argument function is a dead submit button on every form), and that a browser refusing storage returns no key and submits anyway rather than locking a real person out. It pulls `DEVICE_STORE` out of the page too, so the test cannot use a different storage key than the page does |
| `event-phase.test.js` | the status that is worked out rather than pressed (`eventWindow`, `eventPhase`) — that a table with no declared window is untouched, that done beats filled (a finished event must not read as still coming) and running beats both, that an empty Places box means no limit rather than instantly filled, that an end time before its own start is treated as the day's end instead of marking the event over before it began, and that bad input never produces a phase that reads as closed. The rule also exists in SQL (`event_time_phase`); the file records the one case where the two deliberately differ and why |
| `capacity.test.js` | capacity and backup places (`slotsText` from `f/index.html`) — that a form with no capacity says nothing at all, that places count down and read as singular at one, that a backup is told plainly they would be on the backup list rather than have a place, that a closed event says *closed* rather than *full*, and that an over-booked capacity never shows a negative number. The counting itself is done in the database under a row lock and is covered by the checks in `11-capacity-and-backup.sql` |
| `parent-links.test.js` | parent-scoped form links (`recordFormLink`, `childTableOf` from `index.html`, `fmtParentValue` from `f/index.html`) — that a record link is the ordinary form link plus an encoded token on the same page, that the child table is found from the children rather than a pointer on the parent, and that a date on the public page reads as a date but an impossible one (31 February) is shown as recorded instead of silently rolling over to 3 March |
| `new-record.test.js` | adding a record by hand (`newRecordVisible`, `newRecordMissing`, `newRecordData`) — that a question which does not apply carries no answer, that an empty answer stores no key, that only questions being asked can be required, and how the free text behind an "other" choice is kept or dropped. This path writes straight into `app_submissions` with no form page to eyeball, so a row it builds wrongly lands in a live table |
| `archive.test.js` | archiving a table instead of deleting it (`isArchived`, `archivedConfig`, `archiveConfirmText`) — that the flag the 219 imported tables already carry reads the same as one set from the menu, that archiving rebuilds the config without disturbing columns, stages, capacity or parent, that it never mutates the object the page is still holding, that restoring leaves no `archived_*` key behind so a round trip is a no-op, and that the confirm says the three things a person needs before pressing it (nothing is deleted, it can be undone, the public link keeps working). The last few read `index.html` as source: both menus must confirm before archiving, neither may confirm before restoring, the write is gated on `isAdmin`, and `config.archived` may appear raw exactly once — a second hand-written copy is how a table gets hidden from the list but missed by the Archived count |
| `media-field.test.js` | the `media` question type — a question that takes a photo **or** a video (`isFileField`, `isVideoPath`, `isPlayableVideo`, `fileLabel`, `coverHtml`, `photoSectionHtml`, `uploadCap`, plus `isVideoFile`/`sizeText` from `f/index.html`). What the answer *is* has to be decided from the stored R2 key alone, because no MIME type is stored beside it: that a key with no extension reads as an image (every row written before this existed), that `holiday.mp4.jpg` is a JPEG rather than a video, that `.avi` is a video but is offered as a download rather than handed to a player that would show a black rectangle, that a video never becomes an `<img>` or a card thumbnail (there is none — the sweeper builds them from images), and that the gallery heading counts videos honestly instead of calling them photos. The two ceilings live in both pages, the way `condMet` does, so the last tests read both files and fail if only one is raised |
| `delete-selected.test.js` | deleting a ticked selection from the grid (`deleteSelectedRecords`, `paintSelBar`) — the one test file here that tests a **caller** rather than a helper, because `payroll.test.js` passing 16/16 while the export was broken proved that a helper tested in isolation says nothing about who calls it and with what. The database, the R2 bucket, the confirm dialog and the DOM are stubbed and the assertions are about the calls made and their **order**: that a parent's children are deleted *before* the parent (the FK is `ON DELETE SET NULL`, so the other order does not delete them, it orphans them — `parent_id` null, invisible in every view, worth nothing to the payroll export), that a failed child delete stops before the parents are touched, that every file field's upload is removed from the bucket and not just the first, that files go before rows, that 250 ids become chunks of 100/100/50 with nothing lost or repeated, that a reviewer who cannot manage deletes nothing even if the handler is called directly, that cancelling deletes nothing including the files, that the confirm names the child count and pluralises it, that a count the database refuses errs toward warning rather than promising nothing will be lost, and that success clears the ticks and re-reads the table rather than splicing the array and leaving the entry count and footer totals stale |
| `card-customise.test.js` | "Customize cards" — which file question is a card's cover, whether it is cropped or fitted, which fields the card carries and in what order, and whether their names show (`cardPrefs`, `summaryFields`, `cardChoosable`, `cardSave`, `coverHtml`). The rule has three levels and nearly every test is about which one wins: this browser (localStorage) over the table's saved default (`app_tables.config`) over the behaviour every card had before the panel existed. The first test is the one that matters most — with nothing configured and nothing chosen a card must draw exactly as it does today, or the feature is a silent redesign of 226 live tables — and the rest are the ways a choice goes stale or reads wrongly: a cover naming a question since deleted, a cover naming a question that is no longer a file at all, an empty field list read as "nothing chosen" rather than as an empty card (the first chosen field *is* the title), `config.card_no_cover` still meaning no cover on the tables that carry it, and "None" surviving despite being stored as `""` — falsy, so anything testing the value instead of the key hands the cover straight back. The last few read `index.html` as source: a helper nobody calls is a feature nobody has, so they assert the cards read the chosen cover and shape, that field names are switchable, and that "Save for everyone" is gated on `isAdmin` |
| `card-panel.chrome.js` | the same panel, **clicked**: the arrows, the tick boxes, Crop/Fit, the cover radios and Reset, driven in order with the answer read back out of storage. The only file here that needs more than node — headless Chrome, found automatically or named with `CHROME=<path>`, and **skipped rather than failed** when there is none — because reorder and "the last field cannot be unticked" are DOM and events, and a panel whose arrows quietly stopped working would pass every other test in this folder. It lifts the stylesheet and the functions out of `index.html` and stubs `renderCustom` to redraw the panel, which is what the app's own render does |
| `sidebar-groups.test.js` | the sidebar's left edge (`groupByCategory`, plus the two fold headings read out of `index.html` as source). Two rules, both of which arrived as "why do these all look different?" rather than as a bug report about grouping: **a group of one is not a group** — the Airtable migration made one category per base and 37 of them hold a single table, so the sidebar showed a fold arrow, a name and the count "1" and opened onto one table usually called the same thing — and **every row starts at the same x**, which needs the fold arrow in the same 20px slot a table's colour mark occupies instead of as text inside the label. The tests that matter are the ones about *not* losing anything: a flattened table keeps its place in the list rather than being appended after everything else, the category is still on the row so it groups again by itself the moment a second table joins it, and the width of `.side-fold` is compared against `.tmark` in the stylesheet so the two cannot drift |
| `duplicate-table.test.js` | duplicating a table (`duplicate_table` is a database function that verifies itself when applied — see `workspaces/19-duplicate-table.sql`; these test the page). Every test is a way the feature could ship looking finished and not be: the item missing from one of the two ⋯ menus, which are separate code built two separate ways; a non-admin being offered it; the copy being made but never opened, so it is lost in a sidebar of 272 entries; "copy the records too" defaulting to on, which for the biggest table copies 28,000 rows because somebody clicked through a dialog; and a missing migration reading as a permissions problem, which is exactly what `record_share_token` did for a week |
